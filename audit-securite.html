Vulnérabilités et corrections

Élevé Usage de innerHTML avec interpolation de chaînes
Problème

Deux endroits du code construisaient du HTML via innerHTML en interpolant directement des variables : les libellés des options de réponse et le récapitulatif des questions. Si le contenu des questions venait un jour d'une source externe (API, fichier JSON chargé dynamiquement), toute valeur non filtrée pourrait injecter du HTML arbitraire et déclencher du JavaScript — c'est la définition d'une faille XSS stockée.

Code vulnérable 
// Option buttons
btn.innerHTML = `<span class="letter">${letters[i]}</span><span>${opt}</span>`;

// Review list
item.innerHTML = `<span class="dot ${a.correct ? 'ok' : 'ko'}"></span>
  <span>${shuffled[i].text.substring(0, 70)}…</span>`;
Correction appliquée

Remplacement par la création explicite de nœuds DOM avec document.createElement() et affectation via textContent, qui ne parse jamais le contenu en HTML. 

const letterSpan = document.createElement('span');
letterSpan.className = 'letter';
letterSpan.textContent = letters[i];   // jamais interprété comme HTML
const textSpan = document.createElement('span');
textSpan.textContent = opt;
btn.appendChild(letterSpan);
btn.appendChild(textSpan);
Moyen Absence de Content Security Policy (CSP)
Problème

Sans CSP, un attaquant qui parviendrait à injecter du contenu dans la page pourrait charger des scripts depuis n'importe quel domaine externe, exfiltrer des données ou rediriger l'utilisateur. La CSP est la ligne de défense en profondeur contre les XSS.

Correction appliquée

Ajout d'une balise meta CSP restrictive. Elle autorise uniquement les scripts et styles inline (nécessaires pour une page HTML autonome), bloque toute ressource externe, interdit les soumissions de formulaires et les changements de base. 

<meta http-equiv="Content-Security-Policy"
  content="default-src 'none';
           script-src 'unsafe-inline';
           style-src 'unsafe-inline';
           base-uri 'none';
           form-action 'none';" />
Moyen Absence de Referrer Policy
Problème

La page contient un lien externe vers bitwarden.com. Sans politique de référent, le navigateur envoie l'URL complète de la page dans l'en-tête Referer lors du clic. Ce comportement peut révéler à des tiers le contexte de navigation de l'utilisateur, surtout si la page est hébergée sur une URL interne ou contient des paramètres sensibles.

Correction appliquée

Ajout de la balise meta referrer avec la valeur no-referrer, qui supprime l'en-tête pour tous les liens sortants. Le lien disposait déjà de rel="noopener noreferrer", qui couvre le cas du target="_blank" ; la balise meta élargit cette protection à l'ensemble de la page. 

<meta name="referrer" content="no-referrer" />
Faible Algorithme de mélange biaisé
Problème

La fonction shuffle utilisait [...arr].sort(() => Math.random() - 0.5). Cette technique est connue pour produire une distribution non uniforme : certaines permutations ont une probabilité d'apparition significativement plus élevée que d'autres. Dans un quiz, cela signifie que certains ordres de questions reviennent bien plus souvent qu'attendu, réduisant la valeur pédagogique des sessions répétées.

Code vulnérable 
// Biaisé — certaines permutations favorisées
function shuffle(arr) {
  return [...arr].sort(() => Math.random() - 0.5);
}
Correction appliquée

Remplacement par l'algorithme Fisher-Yates (Knuth shuffle), qui garantit une distribution uniforme en O(n) — chaque permutation a exactement la même probabilité d'apparaître. 

function shuffle(arr) {
  const a = [...arr];
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;
}

Conclusion

Les 4 corrections ont été appliquées directement dans quiz-cybersecurite.html et commitées sur la branche de développement. La page ne charge aucune ressource externe, ne collecte aucune donnée et ne soumet rien à un serveur — ce qui en fait une surface d'attaque très réduite. Les corrections apportées (CSP, Referrer Policy, DOM API sûre, Fisher-Yates) renforcent la défense en profondeur et pérennisent le code face à d'éventuelles évolutions futures (contenu dynamique, intégration dans un CMS, etc.).
